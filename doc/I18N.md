# Languages: English and Portuguese (Brazil)

tsundoku has gone to friends who don't all read English. Its words are now
messages, in English (`en`, the base) and Brazilian Portuguese (`pt-BR`), and
each device reads in its own (the owner, 2026-10-31). Card c210 ("i18n:
English and PT-BR, the plumbing and the friend-facing screens") started it;
the screens still in English each have a card (below).

## How it's built

**Paraglide JS 2** (`@inlang/paraglide-js`), the same as Wayfarer. The words
are `messages/en.json` and `messages/pt-BR.json`; the compiler turns each
message into a function in `src/lib/paraglide/` (generated, never tracked).
The options are once, in `paraglide.config.js`: `vite.config.ts` and
`vitest.config.ts` hand them to the plugin, and `yarn run i18n` to the
compiler, which `check` runs first because svelte-check runs without vite.

`project.inlang/settings.json` loads the message-format plugin from a CDN when
the compiler first runs, and caches it in `project.inlang/cache/` (ignored).
A first compile on a fresh checkout therefore needs the network once.

## Which language a device reads

| Order | Where from                                                                              |
| ----- | --------------------------------------------------------------------------------------- |
| 1     | The device's choice: SETTINGS › 08 — DEVICES › APP LANGUAGE, the cookie `tsundoku_lang` |
| 2     | The browser's language (`Accept-Language`)                                              |
| 3     | English                                                                                 |

- **The server decides, the browser reads it back.** `hooks.server.ts` runs
  Paraglide's middleware first (a refusal or a redirect is in the language
  too) with a strategy of our own, `custom-choice`, that reads only our
  cookie, then `preferredLanguage`. It writes the result on `<html lang>`,
  and `hooks.client.ts` makes the client's `getLocale()` read that attribute.
  So the hydrated page can't disagree with the first one.
- **No `cookie` strategy, on purpose.** Paraglide's client writes its cookie
  on the first `getLocale()`, which would pin AUTO to whatever the browser
  said on day one. Our cookie is written only by the choice in SETTINGS.
- **AUTO** (the default) clears the cookie: the browser's language decides
  on every request. A choice is a device value like the theme (`lang` in
  `src/lib/settings/catalog.ts`), mirrored on the workstation, so SETTINGS
  can change another device's. A change reloads the page
  (`routes/+layout.svelte`), since every word is the server's.
- The picker names each language in itself (`ENGLISH`, `PORTUGUÊS (BRASIL)`),
  so it's found by someone who can't read the page around it.

## Writing a screen's words

- **A message per phrase, keyed by area**: `start_title_repo`,
  `help_phone_short_1`, `setup_password_label`. Flat snake_case; the prefix is
  the screen or component (`start`, `first`, `help`, `setup`, `login`,
  `welcome`, `update`, `nav`, `more`, `settings`…).
- **`name_*` are names other screens point at**: a screen, a section, a tab
  (`name_settings`, `name_devices_section`, `name_get_started`). A sentence
  that sends the reader somewhere uses them (`{m.name_settings()} ›
{m.name_devices_section()}`), so the pointer and the place say the same
  word. A screen still in English shows its own name in English until its
  card; that mismatch is the cost of going a screen at a time.
- **Never call a message at module scope.** The language is per request on
  the server, and a constant made at import is made once, in English. Keep a
  table of functions (`{ repo: m.start_title_repo }`) and call it where the
  word is used, or build the words inside the function that returns them.
  HELP's topics are built by `topics()` for this reason.
- **Imports.** Components import `{ m } from '$lib/paraglide/messages'`.
  Modules under `src/lib/library`, `src/lib/server` and `src/lib/help` import
  relatively with the extension (`'../paraglide/messages.js'`), because the
  scripts run them under Node's type stripping, which knows no `$lib`.
- **Numbers** go through `num()` (`src/lib/i18n/format.ts`), never
  `toLocaleString('en-US')`: 1,234 is 1.234 in Portuguese. `upper()` upper-
  cases a title for a mono label by the language's rules.
- **Plurals** are Paraglide variants on a `count` input, with the number
  already formatted as `n`: `m.first_sources({ count, n: num(count) })`.
  Portuguese's `one` covers 0 and 1.
- **A bold word inside a sentence** splits the sentence around it
  (`start_repo_body_a`, `_b` bold, `_c`), so the markup stays in the
  component and neither language carries HTML.
- **Capitals are written, not transformed.** A mono label the design draws
  in capitals is in capitals in both files; where a component already sets
  `text-transform: uppercase`, the message is in sentence case.
- **The English is the copy as it was, verbatim.** The design and the
  specs pin it; a message is not the moment to reword it.
- **Not translated**: tsundoku (lower case), product and source names
  (Mihon, Aniyomi, LNReader, Tailscale, AniList), file names and paths
  (`Mihon/autobackup`, `index.min.json`, `README.TXT`), keys, glyphs
  (`→ ↓ ✓ · ›`), and anything from a source (titles, descriptions,
  release notes).

**A new word goes through `messages/` even on a screen still in English** (the
owner's rule, 2026-10-31). The REFRESH cell and its band are the first of c214's
words to land (`series_refresh`, `series_refresh_none`,
`series_refresh_new` and their siblings, card c220), so the rest of that screen
can keep its English until its card without losing them.

## Tests

`tests/i18n-domain.spec.ts`: both files have the same keys, every message
has words in both, a message's inputs are the same in both, and the cookie
and `<html lang>` are read as described. Specs run in English: the unit
suite has no request, so Paraglide falls to the base locale, and
`playwright.config.ts` pins the browser's locale to `en-US`. A spec that
checks Portuguese sets it (`overwriteGetLocale` in a unit spec; the cookie in
`i18n-flow.e2e.ts`).

## What it doesn't do yet

- Most screens are still in English: c214 (the library, the series screen,
  the readers and the player), c212 (BROWSE, EXTENSIONS, the preview, the
  search, DOWNLOADS), c213 (SETTINGS, HISTORY and the rest). Until then a
  Portuguese page can point at a place still named in English.
- Sizes (`formatBytes`) keep English decimals.
- Offline, the service worker serves the last copy of a screen in whatever
  language it was kept in.
- Release notes are written in English only (`doc/RELEASE.md`).
- Dates still come from dayjs in English where a screen formats one (the update modal's date uses `Intl` and is the exception).
- The search box's commands (`/settings`, `/help`) are English words; a
  Portuguese `/ajuda` doesn't exist.
