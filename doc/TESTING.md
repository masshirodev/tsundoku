# Testing

Two runners with exactly complementary file globs:

| Runner     | Files                | What it covers                                                                 |
| ---------- | -------------------- | ------------------------------------------------------------------------------ |
| Vitest     | `tests/**/*.spec.ts` | Pure domain (`$lib/library`) and the SQL (`$lib/server`), on in-memory SQLite. |
| Playwright | `tests/**/*.e2e.ts`  | The real app in a real browser, against a production build.                    |

A file collected by both would be run twice against different databases. Keep
the names apart.

## What to run

```sh
yarn run check && yarn run lint                    # before every commit
yarn run test --changed origin/main                # the unit specs your change reaches
yarn run test:e2e tests/<what-you-changed>.e2e.ts  # when the UI changed
yarn run test                                      # the whole unit suite, for a broad change
yarn run test:e2e                                  # the whole e2e suite, by hand, when a change worries you
yarn run test:e2e:dependants                       # after every whole e2e run
```

The tiers, cheapest first:

- **Every commit**: `check`, `lint`, and the unit specs the change reaches.
  `--changed` follows the import graph, so a spec that reads the tree from
  disk, which no import reaches, is not selected: run the whole unit suite when
  in doubt.
- **A UI change**: the e2e files of the screens it touches.
- **A broad change**: the whole unit suite, a few minutes.
- **By hand**: the whole e2e suite, then the dependants. Nothing runs it on its
  own, so a change that breaks a screen it did not touch is found by this run,
  in use, or by the release's smoke test. Expect the first whole run after a
  while to be red, and read a red against "Load" below before chasing it.

The last command runs the `duplicates` and `gate` projects on their own,
because a red in any device project leaves them unrun in the whole run
("Load", below).

Always spelled `yarn run`: Yarn 1's builtin `check` shadows the script and exits
0 having typechecked nothing.

The hooks: `pre-commit` runs lint-staged. `pre-push` runs the hook-arming
check, `check`, `lint` and the unit specs the push reaches (`--changed` against
the upstream). The e2e suite stays manual because it builds the app.

CI (`.github/workflows/ci.yml`) runs on a push to main and on every pull
request: `check`, `lint` and the whole unit suite (with ffmpeg and chromaprint
installed, so no spec skips), the tray's `go vet` and `go test -race`, and the
Android apps' unit tests. It runs no e2e spec.

**Generated tables in this file.** The e2e table and the fixtures' count below
are written by `yarn run e2e:table`, never by hand ("E2E specs"). After adding,
removing or moving an e2e file, run it, rewrite the new row's "Why" (it starts
from the file's header comment), and commit the result.
`tests/e2e-table.spec.ts` fails the unit suite while either is stale.

## Temporary folders

Both runners write SQLite databases and data folders under the OS temp folder
(`TMPDIR`, else `/tmp`), so **leave `TMPDIR` on a fast disk**: pointed at a
spinning disk, the migration specs take minutes and time out. Even an NVMe is
slow for them when it is busy, because a climb commits every rung, about 250
fsyncs a case: a wave gate's `TMPDIR` is on disk, and there four specs
(`migrate-anime`, `migrate-devices`, `move-rung57`, `move-rung58`) took 2-4 s a
case alone and ran past vitest's 5 s beside a busy suite. So a spec that climbs
a file database sets `synchronous = OFF` on its own connection first: it tests
the rung, not durability. A vitest timeout printed as `Error:
STACK_TRACE_ERROR` is this: the timeout's message replaced by the stack's
placeholder. On a machine
whose `/tmp` is a tmpfs, every file there is RAM until it is removed, which is
why both suites clean up after themselves:

- **Unit specs**: `tests/vitest.global-setup.ts` makes one
  `tsundoku-specs-*` folder for the run, gives every data folder a default
  inside it, and removes it at teardown, which runs even when a spec process is
  killed. A spec that makes its own temp folder removes it.
- **E2E runs**: one folder per run, below.

**One folder per run.** `tests/helpers/run-dir.ts`, imported first by the
config, makes `<TMPDIR>/tsundoku-e2e-run-<runner pid>` and points `TMPDIR` at
it; every worker and server inherits it, so the shared preview's database and
data folders, each own-server spec's database, the browse and friend worlds and
Chromium's profiles all land there, and two runs never share a folder. The run
removes it at its end and once more as the runner exits (the web servers write
as they stop), and a run removes any folder whose runner is no longer alive. A
run that is killed leaves its folder until the next run on the same `TMPDIR`.

**A killed run's servers are stopped by the next run.** A runner killed
outright (`kill -9`, a closed session) runs no global teardown, so a server a
global setup started is reparented and serves on, with its database deleted
under it by the next run's sweep. So `tests/friend-setup.ts` records its server
in the run's folder (`servers/friend.json`: its pid, the process's start time
from `/proc`, its port), and the sweep (`tests/helpers/run-servers.ts`), before
it removes a folder whose runner is gone, stops each recorded server that is
still the same process (SIGTERM, then SIGKILL after 5 s), and says so:
`[run-dir] stopped the friend server (pid …, port …) left by run …, whose
runner is gone`. A folder whose runner is alive (another checkout's run on the
same `TMPDIR`) is never opened; a recorded pid whose start time no longer
matches is left alone; nothing is stopped by name or pattern. Only folders
under the run's own `TMPDIR` are seen. The browse world's preview is not
recorded, so a killed run leaves it serving.

## Unit specs

Each spec file gets its own process (`pool: 'forks'`, `isolate: true`), and
`tests/vitest.setup.ts` fails loudly if two ever share one. That matters because
`getDb()` memoises the first `DATABASE_PATH` it sees. A spec that touches the
database sets `process.env.DATABASE_PATH = ':memory:'` **before** importing
anything from `$lib/server`, then seeds it with `seedSample()`. The global
setup defaults `DATABASE_PATH` to `:memory:` as well, so no spec opens the
development library's `data/tsundoku.sqlite` by accident.

**`strip-types-db.spec.ts` loads the modules the scripts reach under Node's
own type stripping.** The scripts and timers run `src/lib/server` without
Vite, and Node refuses TypeScript that needs compiling (a parameter property,
an enum). Vitest compiles it happily, and `node --check` passes it, so only a
real import shows it.

**No spec inherits a git hook's environment.** `pre-push` runs the unit specs
with `GIT_DIR` (and the other `GIT_*` variables git sets for a hook) pointing at
the repository being pushed, so a spec that runs `git` in a scratch folder
would act on that repository instead: `build-lock.spec.ts`'s `git init` once
re-initialised the checkout's `.git` as `core.bare = true`.
`tests/vitest.global-setup.ts` deletes every `GIT_*` variable before any spec
process is forked, so every spec, and every script a spec runs, sees a plain
environment; `git-env.spec.ts` pins it. A spec still says `cwd` for each git
call.

**No spec reaches TMDB with a real key.** A shell may export `TMDB_API_KEY` and
`TMDB_API_RC_TOKEN`, and the client reads them at call time.
`tests/vitest.global-setup.ts` deletes them before any spec is forked, and
`playwright.config.ts` deletes them before any server starts, so every suite
starts with **no key**, the state a fresh install is in. A spec that wants
TMDB sets its own key and stubs the fetch (`setTmdbFetch`); an e2e flow that
wants it starts its own preview with `TMDB_API_URL` pointed at a fake
(`tests/tmdb-link-flow.e2e.ts`).

**The fingerprint specs skip on a machine with no chromaprint.**
`anime-fingerprint-db.spec.ts` and `anime-stream-fingerprint-db.spec.ts` run the
real ffmpeg and chromaprint, through ffmpeg's muxer or `fpcalc` (`FPCALC`, else
PATH). Where neither exists, `tests/helpers/chromaprint.ts` asks once per file,
and the cases that fingerprint skip with the reason printed (`skipping the
cases that fingerprint: …`); the others still run. A skip there hides nothing
that ships, because `ops/release/smoke/fingerprint.sh` proves the bundle's
ffmpeg fingerprints. To run them, install chromaprint's `fpcalc` or set
`FPCALC`. To see the skip on a machine that has one, run with
`FPCALC=/nonexistent`.

**Importer specs never read real data.** A real library is copyrighted and
partly explicit. `tests/helpers/` holds a protobuf encoder and a zip writer, and
`mihon-fixture.ts` uses them to synthesise a `Mihon/` folder of the same shape
in a temp directory: a backup with the rating categories, and CBZs whose
ComicInfo matches by URL, by number, or not at all. `hentoid-fixture.ts` does
the same for `H/.Hentoid/`: a finished book, one read partway, a three-chapter
book, and a folder with no JSON. `import-db.spec.ts` runs the real importer
over it. The e2e server gets an empty `LIBRARY_ROOT`, so START SCAN there can
never import into the database the suite asserts against.

## E2E specs

**The browsers are Playwright's own: `yarn run test:e2e:install`** installs
Chromium and Firefox. Every project runs Chromium except one file,
`browse-player-pip-firefox.e2e.ts`, which asks for Firefox with `test.use({
browserName: 'firefox' })` inside the `browse` project. Each Playwright
release pins its own browser revisions (`playwright-core/browsers.json`), so
run the script again after `@playwright/test` changes, or that file fails at
launch with "Executable doesn't exist".

`playwright.config.ts` builds the app, seeds a fresh database in the run's own
temporary folder (never the development one; "One folder per run", above), and
serves it with `vite preview` under a throwaway `TSUNDOKU_TOKEN`. Every test
starts signed in with the session cookie that token derives, except
`auth.e2e.ts`, which starts signed out on purpose. Workers are half the logical
cores (`workers: '50%'`); `--workers` overrides it.

**The projects.** The device projects are the devices the design draws, and a
plain `*.e2e.ts` runs in the first four:

| Project            | Viewport                                                                       |
| ------------------ | ------------------------------------------------------------------------------ |
| `tablet-portrait`  | 800×1280. Also the one device for every `*-flow.e2e.ts`.                       |
| `tablet-landscape` | 1280×800                                                                       |
| `phone`            | Pixel 7                                                                        |
| `desktop`          | 1440×900                                                                       |
| `tv`               | 960×540, no pointer and no hover (Chromium's Blink settings; [`TV.md`](TV.md)) |

`tv` runs `tv-*.e2e.ts` plus the two layout specs. A frame drawn at one
device's viewport runs in that project alone (`DESKTOP_ONLY`,
`TABLET_LANDSCAPE_ONLY` and `PHONE_ONLY` in `playwright.config.ts`), rather than
each file skipping itself elsewhere. The other projects are worlds of their
own: `browse` (BROWSE against a fake extension engine), `friend` (a friend's
install served as a release serves it), `works-frame` and `works-flow` (each
seeding its own database), and `duplicates` and `gate`, which depend on every
device project and run after them ("Load", below). Which file runs where is the
table below.

**`vite preview` holds a streamed page until it ends when the browser asks for
gzip**: with a 6 s schema the first byte came at 6087 ms under
`accept-encoding: gzip` and at 61 ms under `identity`. The release's server
(adapter-node, `scripts/serve.ts`) compresses no page, so it streams. A "paints
first" e2e, one that asserts a page shows before a slow promise in its `load`
settles, therefore asks as the release answers,
`page.setExtraHTTPHeaders({ 'accept-encoding': 'identity' })`, and says why
(`browse-tags.e2e.ts`'s cold-cache preview does). Under gzip every streamed
promise reads as blocking, and the spec would assert the preview's buffering,
not the app.

**Measure a screen only once it has come to rest.** A client-side navigation
slides the next screen 40px in and sheets rise ([`MOTION.md`](MOTION.md)), so a
`boundingBox()` taken at once reads a moving box. `screenSettled(page)` in
`tests/fixtures.ts` waits for the screen's animations; a sheet waits on its own
(`el.getAnimations()`, as `tv-screens.e2e.ts` does).

**A spec turns reveal on with `revealOn(context, base?)`** (`tests/helpers/reveal.ts`),
which runs the `/reveal` command through the context's own request, so the
server's signed cookie lands in the context ([`PRIVACY.md`](PRIVACY.md), "Only
the server can make the reveal cookie"). Never `addCookies` with
`tsundoku_reveal=1`: the server reads that as reveal off. A spec on a server of
its own passes that server's origin, since each signs with the key in its own
database. A unit spec that fakes a request's cookies answers with
`revealValue(session)` from `$lib/server/prefs`, for the session cookie its fake
answers with (`undefined` when it has none).

The shared preview also carries `ORIGIN=http://tsundoku.test:<preview port>`,
the public origin a tailnet install has (`scripts/serve.ts` sets the same
variable there). `vite preview` never builds a request URL from it, so no
spec's routing changes, but the app reads it from `process.env`, where a TV's
paired cookie is a session only on that host ([`SIGN-IN.md`](SIGN-IN.md)), and
`tv-pair.e2e.ts` names the same host in a request's `Host` header. Vite is told
the name too (`__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS`), or it refuses the
request before the app ever sees it.

**The table below is generated**: `yarn run e2e:table` writes it from
`playwright test --list` (its "Runs on" column) and keeps each row's "Why",
which is written by hand; a new file's row starts from its header comment, to
be rewritten. `tests/e2e-table.spec.ts` runs `--check`, so the unit suite is
red while a spec file has no row or a row names the wrong projects. The same
command rewrites the fixtures' count and its "Never moved over" list below the
table, then runs Prettier over this file.

**An e2e file that takes `test` from `tests/fixtures.ts`** (or from
`tests/helpers/hydrated.ts`, the same `test` under its old name; how many do
is the generated count below) gets a `page.goto`, `page.reload`,
`page.goBack` and `page.goForward` that wait for the page to have hydrated,
and a `goto` that waits for the network to settle first: SvelteKit hydrates
after `load`, and a click, a tap or an arrow key that lands before hydration
does nothing. A client-side navigation into the reader doesn't change the
document, so no load state covers it; `readerReady(page)` waits for the
reader's own stylesheet instead (its ground turns true black). A page a spec
makes itself, in a browser it launched (a TV's pointerless Chromium in
`browse-commands`' `onATv`), is not the fixture's and gets none of this until
it is passed through `waitsForHydration(page)` from `tests/fixtures.ts`.
Without it, `browse-commands`' "on a TV, the refusal still shows" case typed
`/hide` before hydration on a loaded box, the bar's form posted without
JavaScript, and the route it held for `/api/command` was never reached, so the
case ran out its 120 s.

**Network quiet is a guess at hydration; the page's own mark is not.**
`networkidle` is 500 ms without a request, and on a loaded machine the last
module arrives and then waits longer than that for the CPU, so the guess comes
true before hydration does. `hydrated(page)` (`tests/helpers/hydration.ts`)
waits for SvelteKit's route announcer (`#svelte-announcer`), which the
framework's root component draws from its own `onMount`, after every component
under it has mounted: the element exists exactly when every handler does. A
document that isn't SvelteKit's (an API's JSON, a page with script off) is not
waited for. `hydrated.ts` is a pass-through of `tests/fixtures.ts` under its
old name, kept for the files that still import it. Count them when you need the
number, by the import's closing `from` so a wrapped import counts too and a
file that only mentions the path does not (`tests/e2e-table.spec.ts`'s fixture
cases do):

```sh
rg -l "from '\./helpers/hydrated'" tests/*.e2e.ts | wc -l
```

`hydrated(page)` is exported from both for a page the fixture didn't make (a
context of a spec's own: `tv-pair`'s TV). The files that do **not** take the
fixture's `test` are the ones this prints (`-U` because Prettier wraps a long
import over several lines, `-P` for the lookbehind that leaves out a
`type`-only `test`; the pattern is `FIXTURE_PATTERN` in
`scripts/e2e-table.ts`, and `tests/e2e-table.spec.ts` fails while the two
differ):

```sh
for f in tests/*.e2e.ts; do rg -UPq '^import\s*\{[^}]*(?<!\btype\s)\btest\b[^}]*\}\s*from\s*\x27(\./fixtures|\./helpers/hydrated)\x27' "$f" || echo "$f"; done
```

Their `test` is `@playwright/test`'s, whose `goto` waits for nothing more
than it is told: neither network quiet nor hydration. They are two kinds. The
first is a person's decision, so it is written by hand, here, and nowhere else:

- **On purpose, to act before hydration:** `browse-tags` and `filters-layout`.

The second, and the count, are generated: `yarn run e2e:table` writes the
block between the `e2e-fixtures` markers from the files, so every e2e file off
the fixtures that the list above does not name lands there.
`tests/e2e-table.spec.ts` fails while the block is not what the generator
would write ("run `yarn run e2e:table`"), and while a name on the hand-written
list takes the fixtures' `test` or is gone, which the generator cannot settle:
take it off the list, or say why it stays.

### Load

The suite runs while the machine is busy, and what it assumes follows from
that. Measured on a 12-thread machine: with other builds and specs running
(load average 21-37) a whole run passed every test it ran; with six CPU burners
on top (59-69) 37 tests failed, nearly all of them the 30 s budget running out
mid-step in a case that passes alone. So:

- **The suite is held green at a busy machine's load, not at any load.** A red
  at a load past about 60 is read as the machine, not the case, unless it is an
  assertion that also fails at a lower load; the open flakes below say which is
  which.
- **Workers are half the logical cores, fixed** (`workers: '50%'`), not capped
  by load. With six CPU burners running, six workers took 14.7 minutes at a
  load average of 13 to 56, three took 17.7 at 20 to 41, and three workers
  failed no fewer tests. Load stretches every step, so a fixed wait that held at
  rest stops holding; fewer workers stretch the run instead and leave the wait
  as wrong as it was.
- **Wait on the page's own state, never on time.** Hydration (`hydrated(page)`,
  above), a response the app sends (`page.waitForResponse` on the report, as
  `browse-anime` waits for `/api/reading`'s `finish`), a mark the app draws when
  it is done (a setting's row is `.saved` once its action answered, which
  `browse-flow` waits for), or the thing that changed (`text-reader-flow`'s turn
  waits for the flow's transform or the chapter's heading to move). A witness
  must be something the action changes, and only it: the reader rewrites `?at=`
  in the URL 800 ms after the previous turn, so a URL read as "this turn
  happened" moves with no click at all. `waitForTimeout` is for asserting that
  nothing happens in a while, and nothing else.
- **Don't wait for the answer you expect before acting**: wait on the app's
  state, then act as the user would, then assert.
- **Never `pauseAt` the clock's own install time.** `install({ time: at })`
  starts a flowing clock, and under load it has moved past `at` before
  `pauseAt(at)` runs: `Cannot fast-forward to the past`. Pause ahead of it, as
  `settings-devices` does at `at + 30 s`.
- **Timeouts are raised only where the step is measured to be slow** under
  load, and the comment says so (`tv-player`'s clip runs at a tenth of its
  speed for the same reason). The raised ones:
  - `offline-flow`'s and `install`'s wait for the service worker to take
    control, 90 s: alone at a load of 20-25 it took 3.4-8.7 s, in a loaded
    whole run 14.2-18.9 s, and past a load of 40 it ran out a 30 s wait, every
    context in the run precaching at once. `install`'s case is 150 s: the
    wait's 90 s, 30 s for the `goto` before it and 30 s for the two CDP calls
    after, so the wait runs whole and fails as itself. Each run puts its figure
    on the result (`controlled after`, in the JSON or HTML report), and a red
    one too: a `test.afterEach` writes `not within N ms` when control never
    came, whether the wait's own 90 s ran out or the test's budget did.
  - `tv-player`'s cases, 90 s: at a load of 15-68 every case took 24-30 s even
    when it passed, each waiting on the right state (the bar's own 4 s, SKIP's
    8 s alone window, the working stream's attach).
  - `works-flow`'s, 60 s: page loads on its own server ran out the 30 s in
    loaded whole runs, where alone its slowest took 17.7 s.
  - `tv-library-top`'s pinned-bars case, 60 s: about twenty-five key presses
    after a cold load took 34.6 s at a load of about 55.
  - `reader-strip-keys`' cases, 60 s: each opens the reader cold and switches
    to the strip before its first key, 11-27 s at a load of 35-50.
  - The Works frame files' `beforeAll` hooks, which wait for their own preview:
    `works-library-frame`, `work-screen-frame` and `work-end-frame`, which then
    make a Work through the app, 120 s; `work-row-frame` and `work-group-frame`,
    which only seed, 90 s.
  - `motion`'s "a deeper screen slides in…" polls 15 s for the back move:
    0.2-4.1 s after the popstate at a load of 40-44, where expect's 5 s ran out
    past 53.

  A client-side navigation is waited on with `page.waitForURL`, which has the
  test's budget, not with `toHaveURL`, which has expect's 5 s: the URL moves
  only once the next screen's data has loaded.

- **A page from a context of the spec's own waits for nothing.** The fixtures'
  `goto` waits for hydration only on the `page` they give; a page from
  `browser.newContext()` (a hook's, a second device's) has Playwright's own
  `goto`, so call `hydrated(page)` after it before the first tap. Without it the
  Works frame hooks pressed SELECT before hydration, nothing happened, and the
  hook waited for GROUP until its budget ran out; with the app's scripts held
  back 2.5 s it failed every time. The same holds for a file whose `test` is
  `@playwright/test`'s (`series-lists-frame`'s `openByTitle`: a server-drawn
  tile is a `<button>`, there before its handler).
- **A passing state read from outside the page can be gone before the read.**
  `motion`'s leaving sheet carries `pointer-events: none` for its leave's few
  hundred ms; polled from the runner, a loaded phone found it already removed.
  The case reads the style inside the page at the moment the leave starts (it
  wraps the sheet's own `animate()`, which is how Svelte runs `out:leave`) and
  asserts that afterwards. A starved page may draw no frame inside a short
  animation at all, so a `requestAnimationFrame` loop is not enough either.
- **A timer the app runs is the app's state; a test that races it loses under
  load.** `tv-player`'s bar hides itself 4 s after a key while the picture
  plays, and BACK at a bare picture leaves the player: a case that pressed BACK
  "to hide the bar" left the player whenever a loaded worker took 4 s to get
  there. Pause the picture when the case doesn't need it playing (a paused
  picture keeps the bar up), or wait for the bar to go by itself
  (`not.toHaveClass(/chrome/)`) instead of pressing. The same goes for a
  setting the case changes: choosing SPEED 1× undoes the clip's tenth-speed
  slowdown, runs it into the 1 s opening, and SKIP INTRO takes the focus by
  design.
- **Never act on a guess at what autoplay did.** Giving autoplay 5 s and then
  pressing ▶❚❚ regardless pauses a picture that autoplay started in the same
  breath. Press only while the control still says Play, and again until the
  picture plays.
- **A gesture with a time window is sent in one go.** The reader's double tap
  is two taps within 250 ms (`src/lib/reader/zoom.ts`), and two
  `page.touchscreen.tap` calls are four round trips to a loaded browser, which
  arrive as two single taps. `doubleTap(page, x, y)` in `tests/helpers/touch.ts`
  sends the four touch events together, so the gap between the taps is the
  browser's. A test that reads "these two arrive together" uses it, or the same
  idea.
- **"Nothing is left" is read where the thing would be.** `works-flow`'s
  `endWork()` waits for the library's `UNGROUPED · <NAME>` band and asks after
  that Work's tile alone. An absence asserted before the page has changed
  passes vacuously, and an absence of "every X" is wrong as soon as two exist.
- **A screen mid-slide is still the screen being read.** The image reader's
  track keeps the outgoing screen unhidden until the slide lands and only the
  incoming one carries `aria-hidden` (`ImageReader.svelte`), so a count taken
  right after a turn can be the old screen's. Wait for the stage to hold one
  screen, then read it, and open the page a case is about by `?p=`, not by
  where a seed left the series.
- **The service worker is allowed everywhere it isn't in the way.** Every fresh
  context registers it, and it precaches the whole build (about 1,400 files)
  from the shared preview: six contexts doing only that took 10-16 s each at a
  load average of 25. Blocking it for every other spec saved under a minute on
  the four device projects and would split the projects around two files, so
  it is not done. The specs that stub requests the worker would answer block
  it themselves (`serviceWorkers: 'block'`, as `browse-player-*`, `tv-player`,
  `text-reader-flow`, `reader-flow`, `motion` and `waiting-flow` do): once the
  worker controls the page, `page.route` never sees a request the worker sends.
  The worker answers the app shell, page images
  (`/api/entries/<id>/pages/<n>`), a novel's whole EPUB
  (`/api/series/<id>/epub`), an episode's file, subtitles and videos, a
  chapter's `pages` and `text`, `/read/<id>`, every navigation and every
  `__data.json` (`src/service-worker.ts`); every other `/api/` request goes
  straight to the network, where `page.route` sees it. A stub on one of the
  worker's paths with the worker allowed is a race the worker wins once it has
  installed.
- **A press held for the app's timer lets go on the app's state.** The reader's
  long press opens the page menu from a 450 ms timer that the release cancels;
  a `hold()` that lets go after 600 ms of the runner's time is handled first by
  a starved page. `cover-menu-flow`'s holds until the menu shows. The same goes
  for any gesture timed by the app.
- **A delay in a fake is a race, too.** A fake that holds an answer for a fixed
  time, inside which the case must act, loses under load. `browse-move-pick`'s
  fake holds a candidate's details until the case has seen its own state (both
  picks' requests sent, and B's given up by the page, which is what the endpoint
  drops B on), then lets it go (`state.held`).
- **A world's own worker is a race, too.** The browse preview's download worker
  starts with its first page load and downloads whatever the world queued from
  the fake engine, which answers: a chapter queued in the seed is downloading
  1.1 s after the first `goto`. `browse-move`'s MOVE case puts its series back
  as seeded at its start, with the queue held off the worker by the queue's own
  backoff (`next_at`). A seeded state a background worker changes is held, or
  waited for, never assumed.
- **A number read before an action is the shared database's of that moment.**
  `filters-flow` reads ALL's total and the filtered tab's `N OF M` from one
  render, since other flows hide and delete series in between. M is only
  bounded from below (greater than the grid's count): nothing in that render
  states ALL's total to compare it with.
- **`scrollY` moves without the app**: the browser's scroll anchoring shifts it
  as images above arrive, with no event. `reader-strip-keys` measures its
  nudges by how far one page slot's top has moved, not by `scrollY`.
- **Whether a fold exists is the app's rule, not a look.** `series-layout`'s
  `openDetails()` asks the media query that `SeriesPanel.svelte` folds on, then
  waits for the line; asking `isVisible()` once returns before the line is
  drawn. A branch on what the page shows waits for the page first, or asks
  what decides it.
- **A toggle is pressed on its state.** The reader's Escape shows the controls
  when they are hidden and hides them when they show, and a navigation the
  strip makes as it settles can hide them first. `reader-strip-keys`' switch to
  the strip presses it only while they show, until they are gone, with the
  mouse moved off the window's edge first, where a pointermove shows them too.
- **The page giving a request up is not the server hearing it.** The compare
  endpoint drops a request on `request.signal`, which fires when the preview's
  Node server sees the socket close: 4-279 ms after the page's `requestfailed`.
  Nothing the test can see marks the server's abort.
- **A request context's pool keeps sockets the server has ended.** Node's server
  closes an idle keep-alive socket after 5 s, and a request sent on it as it
  closes reads `ECONNRESET`. `friend-wifi`'s check after OFF uses a fresh
  `playwright.request.newContext()`.
- **The app's own URL rewrite can outlive its screen.** The image reader writes
  `?p=` 800 ms after it settles on a page; left sooner, the timer fires during
  the trip back and overwrites the series' history entry. `library-flow`'s ←
  case waits for `?p=` first.
- **`--repeat-each` repeats the file, not its world.** Copies of a serial file
  that writes the shared database run at once under `--workers` > 1 and read
  each other's writes, and a world set up once per run (the friend install, the
  browse world) carries one copy's state into the next. Repeat such a file with
  `--workers=1`, and read a repeat of a world-sharing file for its first copy
  only.
- **A flow's writes are a reader's race**: see "Each flow file owns its series"
  and "The readers beside the flows" above.
- **`duplicates` and `gate` depend on every device project**, so any red in
  those leaves their tests "did not run" (a run's larger "did not run" count is
  the rest of each file after its first red in a serial file, or after a failed
  `beforeAll`). A whole run with any device red has not run them. **The run's
  report says so**: `tests/helpers/not-run-reporter.ts`, the config's second
  reporter, ends every run that left tests out with the projects they were in,
  how many, and the reds in the projects each depends on that kept it out, for
  example:

  ```text
  44 did not run, and have not passed:
    works-flow: 23, after a red earlier in the same file (serial, or a failed beforeAll), or the run stopped
    duplicates: 7, because 15 tests it depends on failed:
      [desktop] tests/library-layout.e2e.ts:156 › the bar with the name, …
  ```

  **So after every whole run, run the dependants on their own**, whatever the
  device projects did:

  ```sh
  yarn run test:e2e:dependants
  ```

  It runs `--project=duplicates --no-deps`, then `--project=gate --no-deps`
  (`scripts/e2e-dependants.ts`), and fails if either did, with the first red's
  code. Arguments reach both runs, as in
  `yarn run test:e2e:dependants --reporter=line`. A `--project` of the caller's
  is refused (exit 2, nothing run): it would join each run's own, the one-run
  race below. `--no-deps` is safe here because the two depend on the device
  projects only for their order on the one seeded database, not for anything
  those write. They are **two runs, not one**: `--no-deps` drops the
  `duplicates` → `gate` order as well, so in one run `unlock-gate` enrolls its
  authenticator while `duplicates-flow` is still typing `/reveal`, which then
  waits for the device. Each run has its own temp folder and so its own
  database, which is why the gate's enrolment does not carry into the next.
  Report the dependants' counts beside the whole run's. When the whole run's
  reporter names neither project, they ran there and this step is a repeat.

  **A red that is known and still red can be left out of a whole run**, so the
  dependants run behind it. Today there is none, so a whole run is plain
  `npx playwright test`. When there is one, export its title (the alternatives
  joined with `|`, each a test's own title):

  ```text
  PLAYWRIGHT_SKIP='<one test's title>|<another's>' npx playwright test
  ```

  and put the live expression in this section as a `sh` block, as
  `PLAYWRIGHT_SKIP='…'` at the start of a line; take it out in the commit that
  fixes the test. **That block is the one copy**: `tests/e2e-table.spec.ts`
  reads it from here (`documentedSkip()` in `scripts/e2e-table.ts`) and fails
  while any of its alternatives matches no test's title. Any other form in a
  `sh` block (double quotes, `export`, no quotes) fails the spec rather than
  reading as no expression. Each alternative must match a test's **own** title:
  Playwright's `grepInvert` also matches the file and `describe` names in a
  test's title path, but the check compares only the titles, so an alternative
  naming a file or a `describe` fails it even though it would skip tests. A
  title is left out of every project, so wherever the same test passes it goes
  unrun too, and the reporter does not count a test left out this way: name the
  expression beside the run's result, since a test that was skipped has not
  passed. `PLAYWRIGHT_SKIP` is safe to leave exported for the unit run and for
  `yarn run e2e:table`: the table lists the files the config collects, and
  ignores the variable (`e2e-table.spec.ts` checks it with an expression that
  leaves out every test).

  `PLAYWRIGHT_SKIP` is a regular expression the config gives every project as
  its `grepInvert`. **`--grep-invert` on the command line does not do this**:
  Playwright never applies a command-line filter to a dependency project, so
  the device projects run whole, their reds included, and the dependants are
  skipped as before (`--list` counts as many tests with `--grep-invert` as with
  nothing, and fewer with `PLAYWRIGHT_SKIP`).

**Ports.** A run that needs fixed ports (a CI gate, a second run beside the
first) assigns the eight `PLAYWRIGHT_*_PORT` variables (`PLAYWRIGHT_PORT` and
the `BROWSE`, `DOWNLOADS`, `DOWNLOADS_ENGINE`, `ENGINE`, `FRIEND`, `RANOBE` and
`WORKS` ports), and a run uses the value it is given. A ninth,
`PLAYWRIGHT_REPO_PORT`, is read the same way. Four ports fall back to the OS
when nothing assigns them: the browse world's own preview
(`PLAYWRIGHT_BROWSE_PORT`), its fake engine (`PLAYWRIGHT_ENGINE_PORT`), the fake
extension repositories (`PLAYWRIGHT_REPO_PORT`) and the friend world's install
(`PLAYWRIGHT_FRIEND_PORT`). The runner takes each from the OS once per run,
pinning it where the setup and every worker read them (`tests/browse-world.ts`,
`tests/friend-world.ts`). The browse world's servers name the port they could
not take instead of waiting forever. The friend world's data folder is named
after its port, so it moves with it, and its setup, specs and teardown read the
one pinned value. The two specs that fall back to a written-in `'4194'` for the
browse preview (`tests/tv-move.e2e.ts`, `tests/tv-player.e2e.ts`) are handed the
pinned value through the environment before any worker starts, so the fallback
is never the one a run uses.

**Two invocations can share one checkout**, because `scripts/build-lock.mjs`
wraps the webServer command and keeps apart the two things that collide in
`.svelte-kit/`:

- **Two builds.** The prepare step (the seed, the dictionary copy) and the
  build run under `.svelte-kit/.build-lock`, a file naming its holder's pid. A
  second invocation waits for it.
- **A build under a running preview.** `vite build` empties
  `.svelte-kit/output` first, and a preview serves out of it for as long as its
  run lasts, after the lock is released. So each invocation that serves
  records itself in `.svelte-kit/.build-users/<pid>`, and nobody builds while a
  live one is recorded. An invocation that finds the output in use serves it
  without building when it was built from the tree as it is now (HEAD, the
  tracked changes and the untracked files, hashed into
  `.svelte-kit/.build-stamp`), and otherwise waits for the users to finish: a
  stale build would test code that is no longer there. With nobody serving it
  builds. A lock released at the end of the build instead lets a second run
  rebuild under the first's running previews, whose worlds then refuse
  connections.

Each invocation runs its own prepare step, so each has its own seeded
database. A record whose process is gone is removed by the next run (by pid
and the process's start time from `/proc`, since Playwright's teardown kills
the wrapper before it can remove its own). A wait gives up after 150 s, inside
the webServer's 180, naming whom it waited for: an invocation that starts
while another runs a whole suite on a changed tree fails rather than tests
stale code. A stale lock, whose holder is gone, is taken over by exactly one
waiter: the right to replace it is a ticket named after the dead lock's bytes
(`.build-lock.takeover.<hash>.<n>`), created with `wx`, and its winner renames
its own record onto the lock only while the lock still holds those bytes, so
two waiters that read the same dead holder never both build. A waiter that
finds the ticket taken by a live writer waits, as for any holder; a ticket
whose writer died before its rename is passed by creating the next
(`<n + 1>`), never removed, and the winner removes every ticket once the lock
is its own. A release removes the lock only while it holds the bytes its own
process wrote, so a dead holder's pid reused by a later wrapper cannot release
it. The wrapper never outlives the runner that started it: Playwright stops it
by SIGKILLing its process group, which its commands stay in, and when the
runner is itself killed outright the wrapper sees its parent go within a
second, kills its command's whole tree, removes its record and exits 1, so no
orphan preview keeps later runs waiting. A stale lock taken over and a stale
user removed are each logged (`taking over a stale lock from pid …`,
`removing a stale user …`). `tests/helpers/build-lock.spec.ts` has a case for
each of these.

**The second invocation takes its own `--output`**, such as
`--output temp/playwright/results-2`. Both would otherwise write
`test-results/`, which the config does not move, and a run empties it when it
starts: the second deletes the first's error contexts and attachments while
the first is still writing them.

Give the second invocation its own ports. The browse and friend worlds cannot
share servers or databases: leave the second's `PLAYWRIGHT_BROWSE_PORT`,
`PLAYWRIGHT_ENGINE_PORT` and `PLAYWRIGHT_FRIEND_PORT` unset, so the worlds take
theirs from the OS, and give its `PLAYWRIGHT_PORT` another value (an unset one
falls back to 4183, and two invocations on one preview port share its server
and its database). Both runs share `TMPDIR`; each makes its own folder under it.

### Regenerating the frame spec

The frame files (`library-frame.e2e.ts` and the others marked **Generated** in
the table) are written by a conformance generator from the design files, which
live with the design, outside this repository. Don't hand-edit their generated
assertions, because regenerating overwrites them. Hand-written layout
assertions go in the matching `*-layout.e2e.ts` (`library-layout.e2e.ts` for
the library).

The generator's output names no port: it writes
`process.env.PLAYWRIGHT_BASE_URL ?? ''`, so `page.goto` follows the Playwright
project's own `baseURL`. It also writes `@playwright/test`'s import, and that is
the one line to put back by hand: `./fixtures`' import and the comment above it,
so the shared `page.goto` waits for hydration.
