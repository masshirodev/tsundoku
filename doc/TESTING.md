# Testing

Two runners with exactly complementary file globs, the same split Kumiko uses:

| Runner     | Files                | What it covers                                                                 |
| ---------- | -------------------- | ------------------------------------------------------------------------------ |
| Vitest     | `tests/**/*.spec.ts` | Pure domain (`$lib/library`) and the SQL (`$lib/server`), on in-memory SQLite. |
| Playwright | `tests/**/*.e2e.ts`  | The real app in a real browser, against a production build.                    |

A file collected by both would be run twice against different databases. Keep
the names apart.

## What to run

```sh
yarn run check && yarn run lint && yarn run test   # before every commit
yarn run test:e2e                                  # when the UI changed
yarn run test:e2e:dependants                       # after every whole e2e run
```

The last line runs `duplicates` and `gate` on their own, because a red in any
device project leaves them unrun in the whole run ("Load", below).

Always spelled `yarn run`: Yarn 1's builtin `check` shadows the script and exits
0 having typechecked nothing.

The hooks are copied from Kumiko. `pre-commit` runs lint-staged. `pre-push` runs
the hook-arming check, `check`, `lint` and the unit suite. That last one is
affordable because this repository lives only on the workstation, never on the
throttled VPS. The e2e suite stays manual because it builds the app.

## Unit specs

Each spec file gets its own process (`pool: 'forks'`, `isolate: true`), and
`tests/vitest.setup.ts` fails loudly if two ever share one. That matters because
`getDb()` memoises the first `DATABASE_PATH` it sees. A spec that touches the
database sets `process.env.DATABASE_PATH = ':memory:'` **before** importing
anything from `$lib/server`, then seeds it with `seedSample()`.

**`strip-types-db.spec.ts` loads the modules the scripts reach under Node's
own type stripping.** The scripts and timers run `src/lib/server` without
Vite, and Node refuses TypeScript that needs compiling (a parameter property,
an enum). Vitest compiles it happily, and `node --check` passes it, so only a
real import shows it.

**Importer specs never read real data.** The samples on `/mnt/hdd2` are the
owner's, copyrighted and partly explicit. `tests/helpers/` holds a protobuf
encoder and a zip writer, and `mihon-fixture.ts` uses them to synthesise a
`Mihon/` folder of the same shape in a temp directory: a backup with the
rating categories, and CBZs whose ComicInfo matches by URL, by number, or not at
all. `hentoid-fixture.ts` does the same for `H/.Hentoid/`: a finished book, one
read partway, a three-chapter book, and a folder with no JSON. `import-db.spec.ts` runs the real importer over it. The e2e server gets an
empty `LIBRARY_ROOT`, so START SCAN there can never import into the database the
suite asserts against.

## E2E specs

**The browsers are Playwright's own: `yarn run test:e2e:install`** installs
Chromium and Firefox (c446). Every project runs Chromium except one file,
`browse-player-pip-firefox.e2e.ts`, which asks for Firefox with `test.use({
browserName: 'firefox' })` inside the `browse` project. Each Playwright
release pins its own browser revisions (`playwright-core/browsers.json`), so
run the script again after `@playwright/test` changes, or that file fails at
launch with "Executable doesn't exist" on a box that only had Chromium. Until
wave 20 the script installed Chromium alone, and the Firefox spec passed only
because the workstation's `~/.cache/ms-playwright` happened to hold
`firefox-1543`.

**`vite preview` holds a streamed page until it ends when the browser asks for
gzip** (the series slot's probe, wave 18): with a 6 s schema the first byte
came at 6087 ms under `accept-encoding: gzip` and at 61 ms under `identity`.
The release's server (adapter-node, `scripts/serve.ts`) compresses no page, so
it streams. A "paints first" e2e, one that asserts a page shows before a slow
promise in its `load` settles, therefore asks as the release answers,
`page.setExtraHTTPHeaders({ 'accept-encoding': 'identity' })`, and says why
(`browse-tags.e2e.ts`'s cold-cache preview does). Under gzip every streamed
promise reads as blocking, and the spec would assert the preview's buffering,
not the app.

**Measure a screen only once it has come to rest.** A client-side navigation
slides the next screen 40px in and sheets rise ([`MOTION.md`](MOTION.md)), so a
`boundingBox()` taken at once reads a moving box. `screenSettled(page)` in
`tests/fixtures.ts` waits for the screen's animations; a sheet waits on its own
(`el.getAnimations()`, as `tv-screens.e2e.ts` does).

`playwright.config.ts` builds the app, seeds a fresh database in the run's own
temporary directory (never the development one; see "One folder per run"
below), and serves it with `vite preview`
under a throwaway `TSUNDOKU_TOKEN`. Every test starts signed in with the session
cookie that token derives, except `auth.e2e.ts`, which starts signed out on
purpose.

The projects are the devices the design draws: `tablet-portrait` (800×1280),
`tablet-landscape` (1280×800), `phone` (Pixel 7), `desktop` (1440×900) and `tv`
(960×540, no pointer and no hover -- Chromium's Blink settings stand in for a
remote, see [`TV.md`](TV.md)). One more, `browse`, runs BROWSE's specs against a
server of their own (below).

The shared preview also carries `ORIGIN=http://tsundoku.test:<preview port>`,
the public origin a tailnet install has (`scripts/serve.ts` sets the same
variable there; c245). `vite preview` never builds a request URL from it, so no
spec's routing changes -- but the app reads it from `process.env`, where a TV's
paired cookie is a door only on that host ([`SIGN-IN.md`](SIGN-IN.md)), and
`tv-pair.e2e.ts` names the same host in a request's `Host` header. Vite is told
the name too (`__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS`), or it refuses the
request before the app ever sees it.

**The table below is generated** (c348): `yarn run e2e:table` writes it from
`playwright test --list` (its "Runs on" column) and keeps each row's "Why",
which is written by hand; a new file's row starts from its header comment.
`tests/e2e-table.spec.ts` runs `--check`, so the unit suite is red while a
spec file has no row or a row names the wrong projects. **A wave's merge
regenerates it**: each slot that adds an e2e file leaves this spec red over
its own new files (it cannot edit this file, and another slot's file is not
on its branch), so whoever merges the slots runs `yarn run e2e:table`,
rewrites each new row's "Why" from the slot's notes, runs Prettier over this
file, and commits the table with the merge.

**77 of the 94 e2e files take `test` from `tests/fixtures.ts`** (or from
`tests/helpers/hydrated.ts`, the same `test` under its old name), whose
`page.goto`, `page.reload`, `page.goBack` and `page.goForward` wait for the
page to have hydrated, and `goto` for the network to settle first:
SvelteKit hydrates after `load`, and a click, a tap or an arrow key that
lands before hydration does nothing. That was the suite's recurring flake.
A client-side navigation into the reader doesn't change the document, so no
load state covers it; `readerReady(page)` waits for the reader's own
stylesheet instead (its ground turns true black).

**Network quiet is a guess at hydration; the page's own mark is not**
(c439). `networkidle` is 500 ms without a request, and on a loaded box the
last module arrives and then waits longer than that for the CPU, so the guess
comes true before hydration does. `hydrated(page)` (`tests/helpers/hydration.ts`) waits for
SvelteKit's route announcer (`#svelte-announcer`), which the framework's root
component draws from its own `onMount`, after every component under it has
mounted: the element exists exactly when every handler does. A document that
isn't SvelteKit's (an API's JSON, a page with script off) is not waited for.
Until wave 21 only the specs importing `tests/helpers/hydrated.ts` had this
wait; the fixtures have it since c477, and `hydrated.ts` is now a
pass-through of `tests/fixtures.ts` under its old name, kept for its eighteen
importers (`rg -ln "helpers/hydrated'" tests/`). `hydrated(page)` is
exported from both for a page the fixture didn't make (a context of a spec's
own: `tv-pair`'s TV). The count is a claim, so it is checked
(`tests/e2e-table.spec.ts`, "the fixtures' count"); the files that do
**not** take the fixture's `test` are the ones this prints:

```sh
for f in tests/*.e2e.ts; do rg -q "^import .*\btest\b.* from '(\./fixtures|\./helpers/hydrated)'" "$f" || echo "$f"; done
```

Their `test` is `@playwright/test`'s, whose `goto` waits for nothing more
than it is told: neither network quiet nor hydration. They are two kinds,
and the spec holds these two lists to what the loop prints:

- **On purpose, to act before hydration:** `browse-tags` and
  `filters-layout`.
- **Never moved over, with no reason to stay:** `browse-frame`,
  `browse-list-frame`, `browse-move`, `browse-online`,
  `browse-online-devices`, `browse-preview-frame`, `browse-source-flags`,
  `first-read-frame`, `help-frame`, `import-frame`, `series-lists-frame`,
  `settings-frame`, `start-frame`, `tv-app-pair` and `tv-tags`.

The deliberate ones act as a quick thumb does. `browse-tags`' slow case taps
the preview's link the moment it shows, hydrated or not (its other cases wait
for network quiet in their own `open()`), and `filters-layout` reads and
opens FILTER with "No wait for hydration: a native open before it now
survives it" (c105). `library-top-bar` is a third, and the loop does not
print it: every case takes the fixture's `test` but the FILTER one (c105),
which is `@playwright/test`'s under the name `plain`.

The unmoved ones need one line each, their `test` import from `./fixtures`
instead of `@playwright/test`, made by the slot that owns the file (this
slot's notes, wave 21, list who). The nine `*-frame` files among them say
they were generated by `design-tools/gen-conformance.mjs`, which writes
`@playwright/test`'s import, so regenerating one undoes the move unless the
generator learns the fixture; five generated frames, `library-frame` and

### Load

The suite runs while the box is busy: a wave's gate runs beside six slots'
builds and specs, and the load average has been 30 to 59 on the 12-thread
workstation during gates. What it assumes, and the rules that follow (c439):

- **Workers are half the logical cores, fixed** (`workers: '50%'` in
  `playwright.config.ts`, 6 here), not capped by load. Measured on
  2026-11-03, the box loaded by the other slots plus six `node` CPU burners:
  six workers took 14.7 minutes at a load average of 13 to 56, three took
  17.7 at 20 to 41, and three workers failed no fewer tests. Load stretches
  every step, so a fixed wait that held at rest stops holding; fewer workers
  stretch the run instead and leave the wait as wrong as it was.
- **Wait on the page's own state, never on time.** Hydration
  (`hydrated(page)`, above), a response the app sends
  (`page.waitForResponse` on the report, as `browse-anime` waits for
  `/api/reading`'s `finish`), a mark the app draws when it is done (a
  setting's row is `.saved` once its action answered, which `browse-flow`
  waits for), or the thing that changed (`text-reader-flow`'s turn waits for
  the flow's transform or the chapter's heading to move). A witness must be
  something the action changes, and only it: the reader rewrites `?at=` in
  the URL 800 ms after the previous turn, so a URL read as "this turn
  happened" moved with no click at all (measured in round 2 of wave 19).
  `waitForTimeout` is for asserting that nothing happens in a while, and
  nothing else.
- **Don't wait for the answer you expect before acting** (wave 18): wait on
  the app's state, then act as the user would, then assert.
- **Timeouts are raised only where the step is measured to be slow** under
  load, and the comment says so (`tv-player`'s clip runs at a tenth of its
  speed for the same reason). The one raised in wave 19 is `offline-flow`'s
  wait for the service worker to take control, 90 s; `install`'s same wait
  has the same 90 s since wave 21 (c477), after its 30 s ran out on one to
  four device projects in every loaded whole run of waves 19 and 20 and on
  all four in this wave's baseline. Wave 20 raised `tv-player`'s
  per-case budget to 90 s (c448): at a load average of 15-68 every case took
  24-30 s even when it passed, and all eight reds of that run were the default
  30 s running out, each case waiting on the right state (the bar's own 4 s,
  SKIP's 8 s alone window, the working stream's attach). `works-flow`'s is
  60 s (c439): two of its cases ran out the 30 s in page loads on its own
  server in whole loaded runs, where alone its slowest took 17.7 s. `tv-library-top`'s pinned-bars case is 60 s
  (c439, wave 21): about twenty-five key presses after a cold load took
  34.6 s at a load of about 55 (the `goto` 11.5 s, hydration 3.3 s), every
  step on the right state. And a client-side navigation is waited on with
  `page.waitForURL`, which has the test's budget, not with `toHaveURL`,
  which has expect's 5 s: the URL moves only once the next screen's data
  has loaded, and `books-flow`'s ← ran out of the 5 s with the book still
  open in a loaded run (c439).
- **A passing state read from outside the page can be gone before the read.**
  `motion`'s leaving sheet carries `pointer-events: none` for its leave's
  few hundred ms; polled from the runner, a loaded phone found it already
  removed. The case reads the style inside the page at the moment the leave
  starts (it wraps the sheet's own `animate()`, which is how Svelte runs
  `out:leave`) and asserts that afterwards (c439). A starved page may draw
  no frame inside a short animation at all, so a `requestAnimationFrame`
  loop is not enough either.
- **A timer the app runs is the app's state; a test that races it loses
  under load.** `tv-player`'s bar hides itself 4 s after a key while the
  picture plays, and BACK at a bare picture leaves the player: a case that
  pressed BACK "to hide the bar" left the player whenever a loaded worker
  took 4 s to get there. Pause the picture when the case doesn't need it
  playing (a paused picture keeps the bar up), or wait for the bar to go by
  itself (`not.toHaveClass(/chrome/)`) instead of pressing. The same goes
  for a setting the case changes: `tv-player`'s settings case chose SPEED 1×,
  which undid the clip's tenth-speed slowdown, ran it into the 1 s opening,
  and SKIP INTRO took the focus by design (c448).
- **Never act on a guess at what autoplay did** (c448, as `be2a5fc` did for
  `browse-anime`). `tv-player`'s `play()` gave autoplay 5 s and then pressed
  ▶❚❚ regardless; under load autoplay started in the same breath and the
  press paused it. Press only while the control still says Play, and again
  until the picture plays.
- **A gesture with a time window is sent in one go.** The reader's double tap
  is two taps within 250 ms (`src/lib/reader/zoom.ts`), and two
  `page.touchscreen.tap` calls are four round trips to a loaded browser:
  `reader-flow`'s strip case took two single taps (wave 19). `doubleTap(page,
x, y)` in `tests/helpers/touch.ts` sends the four touch events together, so
  the gap between the taps is the browser's (c439). A test that reads "these
  two arrive together" uses it, or the same idea.
- **"Nothing is left" is read where the thing would be.** `works-flow`'s
  `endWork()` clicked UNGROUP and asserted no Work tile remained: on the Work
  screen, before the redirect to the library landed, that was true with
  nothing ended (the screen has no grid), and on the library with a second
  Work still up it was red (wave 19, r2-tv1). It now waits for the library's
  `UNGROUPED · <NAME>` band and asks after that Work's tile alone (c439). An
  absence asserted before the page has changed passes vacuously, and an
  absence of "every X" is wrong as soon as two exist.
- **A screen mid-slide is still the screen being read.** The image
  reader's track keeps the outgoing screen unhidden until the slide lands
  and only the incoming one carries `aria-hidden` (`ImageReader.svelte`), so
  a count taken right after a turn can be the old screen's. `tv-reader`'s
  spread case pressed on from the page CONTINUE opened (a spread already)
  to a page that stands alone, and passed only when `toHaveCount(2)` caught
  the old spread on its way out: 2 runs in 3 red alone at wave 19, 10 in 10
  at a load of 40 at wave 21's base (c479). Wait for the stage to hold one
  screen, then read it, and open the page a case is about by `?p=`, not by
  where a seed left the series.
- **The service worker is allowed everywhere it isn't in the way.** Every
  fresh context registers it, and it precaches the whole build (about 1,400
  files) from the shared preview. Six contexts doing only that took 10-16 s
  each at a load average of 25, and in a whole loaded run the worker
  `install` and `offline-flow` wait for passed 30 s. Blocking it for every
  other spec was measured on the four device projects (4.7 minutes against
  5.5, the same failures otherwise) and not taken: it would mean projects
  split around two files for a sixth of the time. The specs that stub
  requests the worker would answer block it themselves
  (`serviceWorkers: 'block'`, as `browse-player-*`, `tv-player`,
  `text-reader-flow`, `reader-flow`, `motion` and `waiting-flow` do; the last
  three since c477, for a page image, a series' `__data.json` and three
  screens' `__data.json`): once the worker controls the page, `page.route`
  never sees a request the worker sends. The worker answers the app shell,
  page images (`/api/entries/<id>/pages/<n>`), a novel's whole EPUB
  (`/api/series/<id>/epub`), an episode's file, subtitles and videos, a
  chapter's `pages` and `text`, `/read/<id>`, every navigation and every
  `__data.json` (`src/service-worker.ts`); every other `/api/` request goes
  straight to the network, where `page.route` sees it. A stub on one of the
  worker's paths with the worker allowed is a race the worker wins once it
  has installed: `text-reader-flow`'s Japanese book was set from the seed's
  English EPUB, which the worker fetched past the stub, 1 run in 34
  (wave 19, from the run's trace).
- **A flow's writes are a reader's race**: see "Each flow file owns its
  series" and "The readers beside the flows" above.
- **`duplicates` and `gate` depend on every device project**, so any red in
  those leaves their 8 tests "did not run" (a run's larger "did not run"
  count is the rest of each file after its first red in a serial file, or
  after a failed `beforeAll`). With a known
  base failure red on every run, **a gate never runs `duplicates` and `gate`
  at all**: no whole run in wave 19 before round 2 executed `duplicates-flow`
  or `unlock-gate` once, and wave 19's gate had them in its "12 did not run"
  behind `library-layout:156`. A gate that reports "did not run" has not run
  them. **The run's report says so** (c439):
  `tests/helpers/not-run-reporter.ts`, the config's second reporter, ends
  every run that left tests out with the projects they were in, how many, and
  the reds in the projects each depends on that kept it out, for example:

  ```text
  44 did not run, and have not passed:
    works-flow: 23, after a red earlier in the same file (serial, or a failed beforeAll), or the run stopped
    duplicates: 7, because 15 tests it depends on failed:
      [desktop] tests/library-layout.e2e.ts:156 › the bar with the name, …
  ```

  **So after every whole run, the gate's included, run the dependants on
  their own**, whatever the device projects did:

  ```sh
  yarn run test:e2e:dependants
  ```

  It runs `--project=duplicates --no-deps`, then `--project=gate --no-deps`,
  and fails if either did. `--no-deps` is safe here because the two depend
  on the device projects only for their order on the one seeded database,
  not for anything those write. They are **two runs, not one**:
  `--no-deps` drops the `duplicates` → `gate` order as well, so in one run
  `unlock-gate` enrolls its authenticator while `duplicates-flow` is still
  typing `/reveal`, which then waits for the device (measured in wave 20:
  `duplicates-flow:29` red and 5 did not run in one run; 7 and 1 passed as
  two). Each run has its own temp folder and so its own database, which is
  why the gate's enrolment does not carry into the next. Report the
  dependants' counts beside the whole run's. When the whole run's reporter
  names neither project, they ran there and this step is a repeat.

  Leaving the base failures out by title does not get the dependants run
  under load, and since wave 21 there is nothing filed to leave out. Wave
  19 filed two reds: `library-layout:156`, fixed since `ccf4689` (c489), and
  `tv-reader:24`, which failed 2 runs in 3 alone then, and 10 in 10 alone
  by title at a load of about 40 in wave 21 (with the fixtures' hydration
  wait of c477 already in, which made the race lose every time). Its cause was the test's
  (c479; "A screen mid-slide is still the screen being read", above), and
  since `8e42573` it passes 10 of 10 alone at a load of 45-55 and in a whole
  run. Two more were red in **every** loaded wave-20 run, so the dependants
  ran in none of the six: `install.e2e.ts:6` (the service worker's 30 s; 90
  s since c477; in wave 21's first whole run after it the case took 37 s
  to 60 s on the four devices, each past the old budget) and `work-end-frame.e2e.ts:297` (its
  `beforeAll`'s 30 s, which also leaves `works-frame`'s other tests unrun;
  `reader`'s file in wave 21, whose fix is `test.setTimeout(120_000)` as the
  hook's first line). Neither was ever in the expression, because both
  pass alone and a title left out is a test nobody checks.

  **The expression is for a red that is filed and still red**, named with
  its card, and taken out in the commit that fixes it. Today there is none,
  so a whole run is plain `npx playwright test`. When one is filed, export
  its title (the alternatives joined with `|`, each a test's own title), as
  this slot's whole runs did in waves 19 and 20 while `tv-reader:24` was
  red (the gates ran without it):

  ```text
  PLAYWRIGHT_SKIP='<one test's title>|<another's>' npx playwright test
  ```

  and put the live expression in this section as a `sh` block, as
  `PLAYWRIGHT_SKIP='…'` at the start of a line. **That block is the one
  copy** (c478): `tests/e2e-table.spec.ts` reads it from here
  (`documentedSkip()` in `scripts/e2e-table.ts`) and fails while any of its
  alternatives matches no test's title, and the gate copies it from here.
  Any other form in a `sh` block (double quotes, `export`, no quotes) fails
  the spec rather than reading as no expression. Each alternative must match
  a test's **own** title: Playwright's `grepInvert` also matches the file and
  `describe` names in a test's title path, but the check compares only the
  titles, so an alternative naming a file or a `describe` fails it even
  though it would skip tests.
  With no such line, the spec has nothing to check, which is the state at
  wave 21. A title is left out of every project, so wherever the same test
  passes it goes unrun too (`library-layout:156`, while it was in here, left
  the tablets, the phone and the TV unrun with it); the reporter does not
  count a test left out this way, so name the expression beside the run's
  result. `PLAYWRIGHT_SKIP` is safe to leave exported for the unit run and
  for `yarn run e2e:table`: the table lists the files the config collects,
  and ignores the variable (`e2e-table.spec.ts` checks it with an expression
  that leaves out every test).

  `PLAYWRIGHT_SKIP` is a regular expression the config gives every project
  as its `grepInvert`. **`--grep-invert` on the command line does not do
  this**: Playwright never applies a command-line filter to a dependency
  project, so the device projects run whole, their reds included, and the
  dependants are skipped as before (measured: `--list` counts 710 tests with
  `--grep-invert`, the same as with nothing, and 704 with `PLAYWRIGHT_SKIP`).
  Name what you left out beside the run's result: a test that was skipped
  has not passed.

**One folder per run.** `tests/helpers/run-dir.ts`, imported first by the
config, makes `<TMPDIR>/tsundoku-e2e-run-<runner pid>` and points `TMPDIR` at
it; every worker and server inherits it, so the shared preview's database and
data folders, each own-server spec's database and the browse and friend
worlds all land there, and two runs never share a folder (the shared
preview's `tsundoku-e2e-home`, `-empty-library` and `-backups` used to be one
folder for every run on the box). The run removes it at its end and once more
as the runner exits (the web servers write as they stop), and a run removes
any folder whose runner is no longer alive. Before wave 19 every run left its
databases in `/tmp`, which is RAM here. Keep `TMPDIR` on the worktree's
`temp/playwright` anyway: a run that is killed leaves its folder until the
next.

**Ports.** The gate and each slot assign the eight `PLAYWRIGHT_*_PORT`
variables. The fake extension repositories' port is never assigned: the
runner takes a free one from the OS once and every process reads the same
(`tests/browse-world.ts`, c340), and the browse world's servers name the port
they could not take instead of waiting forever.

### Regenerating the frame spec

`library-frame.e2e.ts` is written by the design tools. Don't hand-edit it,
because regenerating overwrites it. Hand-written layout assertions go in
`library-layout.e2e.ts`.

```sh
T=~/.config/myconf/design-tools
node $T/extract-spec.mjs "doc/design/handoff/Index Library.dc.html" --out temp/design/spec.json
node $T/gen-conformance.mjs temp/design/spec.json --init --screen 0 --out temp/design/map.json
# fill in "app" selectors: continueList .cont, continueRow .cont > .row:nth-child(1),
# grid .grid, tile .grid > .tile:nth-child(1); baseUrl http://localhost:4183
node $T/gen-conformance.mjs temp/design/spec.json --map temp/design/map.json --out tests/library-frame.e2e.ts
```
